1. Introduction
1.1 Purpose
This Software Requirements Specification defines the requirements of the ASTU Stock Management System.
The document describes what the system should do, who will use it, the system's functional and non-functional requirements, business rules, data requirements, user stories, use cases, and acceptance criteria.

1.2 Project Overview
The ASTU Stock Management System is a web-based application designed to help Adama Science and Technology University manage inventory digitally.
The system will replace or reduce manual stock management processes and provide a centralized platform for recording, monitoring, issuing, receiving, and reporting inventory.

1.3 Scope
The first version of the system will include:
    • Authentication 
    • User management 
    • Role-based access 
    • Dashboard 
    • Inventory management 
    • Category management 
    • Supplier management 
    • Stock receiving 
    • Stock issuing 
    • Stock tracking 
    • Search and filtering 
    • Reports 

1.4 Intended Audience
This document is intended for:
    • Project supervisor 
    • Project manager 
    • Backend developers 
    • Frontend developers 
    • UI/UX designers 
    • Software testers 
    • System administrators 
    • Future maintenance developers 
    • University stakeholders

3. Functional Requirements
Functional requirements describe what the system must do.
Each requirement has a unique ID so that it can later be connected to design, code, and testing.

3.1 Authentication Requirements
FR-AUTH-001
The system shall allow registered users to log in using valid credentials.
FR-AUTH-002
The system shall reject invalid login credentials.
FR-AUTH-003
The system shall allow authenticated users to log out.
FR-AUTH-004
The system shall prevent unauthenticated users from accessing protected pages.
FR-AUTH-005
The system shall provide role-based access to protected functionality.
FR-AUTH-006
The system shall securely store user passwords.

3.2 User Management
FR-USER-001
The Administrator shall be able to create a user account.
FR-USER-002
The Administrator shall be able to view registered users.
FR-USER-003
The Administrator shall be able to update user information.
FR-USER-004
The Administrator shall be able to deactivate a user.
FR-USER-005
The Administrator shall be able to assign a role to a user.
FR-USER-006
The system shall prevent unauthorized users from managing users.

The system shall require authentication for protected functionality.
NFR-SEC-002
The system shall implement role-based access control.
NFR-SEC-003
Passwords shall not be stored as plain text.
NFR-SEC-004
The system shall validate user input.
NFR-SEC-005
The system shall prevent unauthorized access to protected resources.

4.2 Performance
NFR-PERF-001
The system should provide responsive interactions under normal usage.
NFR-PERF-002
Database queries should be optimized to avoid unnecessary delays.
NFR-PERF-003
The API should return responses within an acceptable time under normal system load.

4.3 Usability
NFR-USE-001
The system shall provide clear navigation.
NFR-USE-002
The interface shall use consistent design patterns.
NFR-USE-003
Error messages shall be understandable to users.
NFR-USE-004
Common tasks should require minimal steps.

4.4 Reliability
NFR-REL-001
The system shall handle errors without crashing.
NFR-REL-002
The system shall maintain data consistency during stock transactions.
NFR-REL-003
The system should provide appropriate feedback after important operations.

4.5 Availability
NFR-AVL-001
The deployed system should be available to authorized users whenever the hosting environment is operational.

4.6 Scalability
NFR-SCAL-001
The architecture should allow additional users and inventory records to be supported as usage increases.
NFR-SCAL-002
The system should allow additional features to be added without requiring a complete redesign.

4.7 Maintainability
NFR-MAIN-001
The codebase shall use a modular structure.
NFR-MAIN-002
The project shall use Git for version control.
NFR-MAIN-003
The project shall use GitHub for source-code collaboration and management.
NFR-MAIN-004
The project shall maintain appropriate technical documentation.

4.8 Portability
NFR-PORT-001
The system should be deployable in different environments using Docker containers.

US-002
As a user, I want to log out so that my account is protected when I finish using the system.

User Management
US-003
As an Administrator, I want to create users so that authorized employees can access the system.
US-004
As an Administrator, I want to assign roles so that users only access permitted functionality.

Inventory
US-005
As a Store Keeper, I want to add inventory items so that I can maintain accurate stock records.
US-006
As a Store Keeper, I want to edit inventory information so that incorrect information can be corrected.
US-007
As a Store Keeper, I want to search inventory so that I can quickly find an item.

Receiving
US-008
As a Store Keeper, I want to record received stock so that inventory quantities remain accurate.

Issuing
US-009
As a Store Keeper, I want to issue stock to departments so that stock distribution is recorded.

Reports

As a Finance Officer, I want to view relevant inventory reports so that I can support financial monitoring.

6.2 Use Case: Login
ID: UC-001
Actor: All users
Precondition: User has a registered account.
Main Flow:
    1. User opens login page. 
    2. User enters email/username. 
    3. User enters password. 
    4. User submits the form. 
    5. System validates credentials. 
    6. System authenticates the user. 
    7. System redirects the user to the appropriate dashboard. 
Alternative Flow:
If credentials are incorrect:
    1. System rejects login. 
    2. System displays an error message. 
    3. User can try again. 
Postcondition:
The authenticated user receives access according to their role.

6.3 Use Case: Add Inventory
ID: UC-005
Actor: Store Keeper
Precondition: User is authenticated and authorized.
Main Flow:
    1. User opens Inventory. 
    2. User selects Add Item. 
    3. User enters item information. 
    4. System validates the information. 
    5. System checks required fields. 
    6. System saves the item. 
    7. System displays a success message. 
Alternative Flow:
If required information is missing:
    • System displays validation errors. 
    • Item is not saved. 

6.4 Use Case: Receive Stock
ID: UC-008
Actor: Store Keeper
Main Flow:
    1. User opens stock receiving. 
    2. User selects inventory item. 
    3. User enters quantity. 
    4. User selects supplier. 
    5. User submits the transaction. 
    6. System validates the transaction. 
    7. System increases stock quantity. 
    8. System records the transaction. 

6.5 Use Case: Issue Stock
ID: UC-009
Actor: Store Keeper
Main Flow:
    1. User opens stock issuing. 
    2. User selects an item. 
    3. User enters quantity. 
    4. User enters requesting department. 
    5. User enters recipient information. 
    6. System checks available quantity. 
    7. System decreases inventory. 
    8. System records the transaction. 
Alternative Flow:
If requested quantity is greater than available stock:
System rejects the transaction and displays an insufficient-stock message.

6.6 Use Case: Generate Report
ID: UC-012
Actor: Authorized User
Main Flow:
    1. User opens Reports. 
    2. User selects report type. 
    3. User selects optional filters. 
    4. System retrieves relevant data. 
    5. System generates the report. 
    6. User views the report. 

7. Business Rules
Business rules define important rules that the software must follow.
BR-001
Every inventory item must have a unique identifier.
BR-002
Inventory quantity cannot be negative.
BR-003
Stock cannot be issued when the requested quantity exceeds available stock.
BR-004
Only authorized users can modify inventory.
BR-005
Every stock receiving transaction must increase the relevant stock quantity.
BR-006
Every stock issuing transaction must decrease the relevant stock quantity.
BR-007
Every stock transaction must have a transaction date.
BR-008
Every stock transaction must identify the responsible user.
BR-009
Users can only access functions permitted by their roles.
BR-010
Deactivated users cannot log into the system.

10. Acceptance Criteria
Acceptance criteria define when a requirement is considered successfully implemented.

Authentication
Requirement: User login.
Acceptance Criteria:
    • User can enter valid credentials. 
    • Valid credentials allow access. 
    • Invalid credentials are rejected. 
    • Appropriate error messages are displayed. 
    • Unauthorized users cannot access protected pages. 

Inventory
Requirement: Add inventory item.
Acceptance Criteria:
    • Authorized user can open the Add Item form. 
    • Required fields are validated. 
    • Item is saved successfully. 
    • Item appears in inventory. 
    • Duplicate identifiers are rejected. 

Stock Receiving
Requirement: Receive stock.
Acceptance Criteria:
    • User selects an existing item. 
    • User enters a valid quantity. 
    • System increases stock quantity. 
    • Transaction is recorded. 
    • User receives confirmation. 

Stock Issuing
Requirement: Issue stock.
Acceptance Criteria:
    • User selects an item. 
    • User enters quantity. 
    • System checks available stock. 
    • Valid transaction decreases stock. 
    • Transaction is recorded. 
    • System rejects insufficient stock.
