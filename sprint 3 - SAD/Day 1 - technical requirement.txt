Welcome to Sprint 3. 🎯

1. First, Understand the Difference
You already have functional requirements from Sprint 1.
Example:
FR-01: The system shall allow authorized staff to add a new inventory item.
Now we translate that into technical requirements.
Functional Requirement
User
 ↓
Add Inventory Item
Technical Requirements
Frontend
 ↓
Add Item Form
 ↓
POST /api/inventory
 ↓
Express Backend
 ↓
Validation
 ↓
MongoDB
So:
Functional requirement = What the system must do.
Technical requirement = What technical capabilities are needed to make it happen.

2. Why Do We Need Technical Requirements?
Imagine you tell a developer:
"Build an inventory system."
They will immediately have questions:
    • Which frontend?
    • Which backend?
    • Which database?
    • How do users log in?
    • Who can add inventory?
    • How does frontend communicate with backend?
    • What happens if the internet fails?
    • How are passwords protected?
    • How is the application deployed?
    • How do we run it on another computer?
Technical requirements remove that uncertainty before development begins.
This is especially important because your advisor asked for:
modern SDLC, Agile, Dockerizing, Git and GitHub
So we need to turn those expectations into concrete technical requirements.

4. Let's Convert Requirements into Technical Requirements
Let's take a simple requirement.
Requirement
The Store Keeper can add an inventory item.
We can break it down.
Frontend Requirement
The React application must provide an Add Item form containing:
Item Name
Item Code
Category
Supplier
Quantity
Minimum Stock Level
Description
[Save]
Backend Requirement
Express must provide:
POST /api/inventory
The backend must:
    1. Receive the request.
    2. Validate the data.
    3. Check whether the item code already exists.
    4. Create the item.
    5. Save it to MongoDB.
    6. Return an appropriate response.
Database Requirement
MongoDB must store something similar to:
InventoryItem
├── name
├── itemCode
├── category
├── supplier
├── quantity
├── minimumStockLevel
├── description
├── createdAt
└── updatedAt
Security Requirement
Only authorized users should be allowed to create inventory items.
Now one simple sentence has become a real technical specification.

Let's understand each.

6. Technology Requirements
These answer:
What technologies will we use?
For example:
Frontend: React
Backend: Node.js + Express
Database: MongoDB
Version Control: Git + GitHub
Containerization: Docker
Problem Solved
Without this, different developers might make different technology choices.
For example:
Developer A → React
Developer B → Angular
Developer C → Vue
That would create unnecessary problems.

7. Frontend Technical Requirements
These answer:
What must the React application be capable of doing?
For example:
TR-FE-01

TR-FE-02

TR-FE-03
The frontend shall communicate with the backend through REST APIs.

TR-FE-04

TR-FE-05

10. Security Requirements
This is extremely important for a stock management system.
We don't want:
Anyone
   ↓
/api/inventory
   ↓
Delete everything 😨
Instead:
User
 ↓
Login
 ↓
Authentication
 ↓
Authorization
 ↓
Permission check
 ↓
API
Examples:
TR-SEC-01
Users shall authenticate before accessing protected resources.

TR-SEC-02
Passwords shall be securely hashed.

TR-SEC-03
Protected API endpoints shall require authentication.

TR-SEC-04
The system shall enforce role-based access control.

TR-SEC-05
Sensitive configuration values shall be stored using environment variables.
We'll study authentication and authorization more deeply on Day 7.

11. Performance & Reliability
We also need to think beyond:
"Does it work?"
We need:
"Does it continue working well?"
For example:
TR-PERF-01
The system should provide reasonable response times
for normal inventory operations.

TR-PERF-02
The system shall display loading states while
waiting for API responses.

TR-REL-01
The backend shall return meaningful error responses.

TR-REL-02
The application shall handle failed API requests
without crashing the frontend.
Don't worry about exact performance numbers yet. We can define appropriate measurable targets later if the project needs them.

13. One Very Important Concept: Non-Functional Requirements
You'll hear this term frequently in software engineering.
There are two major types:
Functional
What does the system do?
Examples:
Add inventory
Update inventory
Delete inventory
Receive stock
Issue stock
Generate reports
Login
Non-Functional
How well or under what constraints does it work?
Examples:
Security
Performance
Reliability
Usability
Scalability
Maintainability
Availability
Think:
Functional
     ↓
WHAT?

Non-functional
     ↓
HOW WELL?
