Today we answer an important question:
Where does everything belong in the system, and how do users navigate between pages?

1. What is Information Architecture?
Information Architecture (IA) means organizing the application's:
    • Pages 
    • Features 
    • Information 
    • Navigation 
    • Menus 
    • Relationships between screens 
so users can easily find what they need.
Think of it like organizing a large building.
If ASTU has a building:
Building
│
├── Administration
├── Finance
├── Library
├── Laboratory
└── Store
You don't put the laboratory inside the library.
Similarly, in our software:
ASTU Stock Management System
│
├── Dashboard
├── Inventory
├── Stock
├── Suppliers
├── Reports
└── Administration
We need to organize the system logically.

2. Why Do We Need Information Architecture?
Without IA, you might build a navigation like:
Dashboard
Users
Reports
Add Item
Suppliers
Issue
Settings
Inventory
Receive
Categories
History
Everything is mixed together. ❌
A Store Keeper might ask:
"Where do I find Receive Stock?"
Instead, we organize related functions:
Inventory
├── Items
├── Categories
└── Stock Levels

Stock Transactions
├── Receive Stock
├── Issue Stock
└── Stock History
Now the structure makes sense.

3. IA vs User Flow
This distinction is very important.
Information Architecture
Answers:
"What exists and where is it located?"
Example:
Stock
├── Receive
├── Issue
└── History
User Flow
Answers:
"How does a user accomplish a specific task?"
Example:
Dashboard
 ↓
Stock
 ↓
Receive
 ↓
Select Item
 ↓
Enter Quantity
 ↓
Confirm
So:
Information Architecture
        ↓
   System Structure

User Flow
        ↓
   User Journey

4. What is a Sitemap?
A sitemap is a visual representation of the application's page hierarchy.
For example:
ASTU Stock Management System
│
├── Login
│

    │
    ├── Inventory
    │
    ├── Stock
    │
    ├── Suppliers
    │
    ├── Reports
    │
    └── Administration
It is essentially the map of our application.

6. Let's Think Like a User
This is where UX becomes interesting.
Imagine you are a Store Keeper.
You log in.
What do you expect to see?
Probably:
Dashboard
Inventory
Receive Stock
Issue Stock
Suppliers
Reports
You probably don't want to see:
Database Configuration
API Management
System Architecture
JWT Configuration
MongoDB
Docker
Why?
Because those are developer concerns, not user tasks.
This gives us an important principle:
The application's navigation should be organized around user goals, not around how developers implement the system.

We could have:
Dashboard
Inventory
Receive
Issue
Suppliers
Reports
But another option is:
Dashboard
Inventory
Stock Management
    ├── Receive
    ├── Issue
    └── History
Suppliers
Reports
The second is more logically grouped because:
Receive
Issue
History
are all stock transactions.
This is an IA decision.

9. Inventory vs Stock
This distinction is important for our project.
Inventory
Describes what items exist.
Example:
Printer Paper
A4 Notebook
Desk
Office Chair
Computer
Stock
Describes what happens to quantities.
Example:
Received 100
Issued 20
Remaining 80
Therefore:
Inventory
   ↓
"What items do we have?"

Stock Management
   ↓
"What happened to those items?"
This helps justify our navigation structure.

10. Dashboard Information Architecture
The Dashboard shouldn't just be a random collection of cards.
It should answer important questions.
For a Store Keeper:
What do I need to know right now?
Possible dashboard structure:
Dashboard
│
├── Summary
│   ├── Total Items
│   ├── Total Stock
│   ├── Low Stock Items
│   └── Recent Transactions
│
├── Low Stock
│
├── Recent Stock Activity
│
└── Quick Actions
    ├── Receive Stock
    ├── Issue Stock
    └── Add Item
This connects directly to our Day 1 UX goals.

11. Role-Based Information Architecture
Now we introduce another important concept.
Not every user should have the same navigation.
For example:
Administrator
Dashboard
Inventory
Stock
Suppliers
Reports
Users
Roles
Settings
Store Keeper
Dashboard
Inventory
Stock
Suppliers
Reports
Management
Dashboard
Reports
The user should not necessarily see:
Users
Roles
Permissions
if they don't have permission to manage users.

12. Why is This Important?
Suppose a Store Keeper sees:
Dashboard
Inventory
Stock
Suppliers
Reports
Users
Roles
Permissions
System Settings
Audit Logs
Database
API
That's overwhelming.
We call this cognitive overload.
A better approach is:
Show users what they need
         +
Hide what they don't need
         +
Keep navigation predictable
This improves UX.
